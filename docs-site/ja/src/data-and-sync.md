# データと同期 {#data-and-sync}

tsumiba は、あなたのデータを**1 つのフォルダーの中の普通のファイル**として保存します。これは意図したことです。
tsumiba があってもなくても、バックアップし、同期し、grep し、好きなエディタで開けます。`tsumiba paths` で
フォルダーの場所が分かります。システムごとの場所は[設定](configuration.md#where-things-are)にあります。

## 構成 {#the-layout}

```text
<データフォルダー>/
├── index.json                  ピン留めと、各ファイルについて分かっていること
├── notes/
│   ├── 01a148d44c055be0439c.md     メモ 1 つにつき 1 つの Markdown ファイル
│   └── …
├── files/
│   ├── 01a148d44c5b4e5d2364/       保存したファイル 1 つにつき 1 つのフォルダー
│   │   └── screenshot.png          …その中に、元の名前のままファイルがある
│   └── …
├── trash/
│   └── 1760719443123_01a1…/        削除した項目。30 日間保持
└── tsumiba.log
```

**ID。**メモとファイルにはそれぞれ、小文字の 16 進数 20 桁の ID があります。作成時刻のミリ秒(12 桁)に、
8 桁の乱数が続きます。ID は作成時刻順に並び、ID から作成時刻を読み取れるので、作成時刻はほかのどこにも
保存されません。

**メモ**は `notes/<id>.md` で、UTF-8、入力したそのままです。メモの*更新日時*はファイルの更新日時です。
メモについて、ファイル自体に入っていない唯一の情報が、ピン留めされているかどうかで、これは
`index.json` にあります。

**ファイル**にはそれぞれ専用のフォルダー `files/<id>/` があり、そのため `photo.png` という名前の 2 つの
ファイルがぶつかることはありません。*リンク*の場合は、そこには何も保存されません。場所は `index.json` に
記録され、元のファイルには手を触れません。

**`index.json`** には、ピン留めされたメモの ID と、ファイルごとの名前・サイズ・追加日時・ピン留めの有無・
取得元、そしてリンクなら元のパスが入っています。アトミックに書き込まれる(新しいファイルを書いて古い
ファイルの上にリネームする)ので、クラッシュしても中途半端なファイルが残ることはありません。

## 自己修復 {#it-repairs-itself}

フォルダーから分かることは、すべてフォルダーから導かれます。tsumiba は、起動時と、積み場を開くたびに、
フォルダーをもう一度調べます。

- 知らない `notes/<id>.md` は、メモとして**取り込まれ**ます。
- ファイルが無くなったメモは、一覧から外れます。
- ファイルが変更されたメモ(エディタや同期ツールによる)は、**再読み込み**されます。
- 知らない `files/<id>/` フォルダーは取り込まれ、中のファイルから名前が取られます。
- フォルダーが無くなった保存済みファイルは、外れます。
- 元のファイルが無くなったリンクは積み場に残り、**見つかりません**と表示されます。

つまり、`notes/` に `.md` ファイルを置いたり(正しい ID の名前にします)、フォルダーから手で消したりしても、
積み場がそれに追従します。

`index.json` が読めない場合(またはこの tsumiba より*新しい*版が書いたものだった場合)、tsumiba はそれを
`index.json.corrupt-<時刻>` として脇へ移し、そのことを伝え、フォルダーから再構築します。失われるのは、
インデックスにしか無かったものだけです。**ピン留め**、ファイルの**取得元アドレス**、そして**リンク**
(インデックスにしか存在しません)。メモとコピーしたファイルは、すべてそのまま残っています。

## ゴミ箱 {#the-trash}

メモを削除したり保存済みファイルを外したりすると、壊してしまう代わりに `trash/<時刻>_<id>/` に移されます。
各エントリには `meta.json`(それが何だったか)と `payload`(メモのテキスト、またはファイルのフォルダー)が
入っています。**30 日**より古いエントリは、tsumiba の起動時に削除されます。リンクを外した場合は
`meta.json` だけが残ります。元のファイルには触れていないので、payload が無いのです。

アプリの*元に戻す*ボタンは、すぐに項目を復元します。あとから手作業で復元するには:

- **メモ:**`payload` を `notes/<id>.md` へ移動します(ID は、エントリのフォルダー名のアンダースコア
  のあとにあります)。
- **ファイル:**`payload` フォルダーを `files/<id>` へ移動します。次に積み場がフォルダーを調べるときに
  取り込まれます(ピン留めと取得元は、必要なら `meta.json` に書いてあります)。

`trash/` の中の、tsumiba が認識しない名前のものは、そのまま残されます。

## 同期 {#syncing}

メモは一意な名前の単独ファイルなので、フォルダーは Syncthing・Dropbox・iCloud Drive・Git リポジトリ・
単なる `rsync` と相性が良好です。助言をいくつか。

- **`notes/` と `files/` を同期し、`index.json` は除外してください。**2 台が同時に変更しうるのはこの
  ファイルだけで、同期ツールが作る競合コピーは無視されますがマージはされません。各マシンは届いたものを
  取り込みます(上記参照)。失うのはマシン間でのピン留めと取得元だけで、ほかは失いません。
- **変更が見えるのは、積み場を開いたとき**で、すでに開いているあいだにリアルタイムで反映されるわけでは
  ありません。
- **同じメモを 2 台で同時に編集する**のは、同期でよくある競合です。ツールは片方を残すか、別の名前でコピーを
  作ります。名前が正しい ID でないコピーはメモではないので、無視されます。フォルダーの中で見つけて、
  手でマージしてください。
- 設定フォルダーをマシン間で同期しないでください。少なくとも `token` と `server.json` は同期しないで
  ください。トークンはマシンごとに別であるべきです。

マシンごとに好きなフォルダーを使うには、`TSUMIBA_DATA_DIR` を設定します(`TSUMIBA_HOME` ですべてを
[まとめて移動](configuration.md#environment-variables)することもできます)。アプリ、コマンドライン、
自動起動の登録のすべてから見えるよう、この変数はログイン時の環境に設定してください。

## バックアップ {#backing-up}

データフォルダー(と、必要なら `config.toml`)をコピーしてください。メモの書き込み途中をコピーしないよう、
tsumiba が待機中か、終了しているときに行います。復元は、それを戻すだけです。積み場は見つけたものを
取り込みます。

## すべてを削除する {#removing-everything}

tsumiba を終了して、データフォルダーと設定フォルダーを削除します。tsumiba が書き込むのはそれだけです
(*ログイン時に起動*をオンにしていた場合は、そのログイン項目も)。
