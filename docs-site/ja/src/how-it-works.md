# 仕組み {#how-it-works}

興味のある方と、開発に参加する方のための短い案内です。コードは読める程度に小さく、このページはその地図です。

## 2 つのクレート {#two-crates}

- **`tsumiba-core`** には、ウィンドウもネットワークのコードもありません。**ストア**(ディスク上のメモとファイル)、
  `config.toml`、API トークン、実行中のインスタンスがコマンドライン向けに残す記録、そして HTTP API の
  リクエストとレスポンスの型です。ほかはすべてこの上に作られ、そのテストにはディスプレイが要りません。
- **`tsumiba`** はプログラム本体です。ウィンドウ(egui/eframe)、HTTP サーバー、コマンドライン、そして
  プラットフォーム層(ポインター、モニター、ショートカット、トレイ、自動起動)が入っています。

## 眠るウィンドウ {#a-window-that-sleeps}

ウィンドウは**一度だけ、隠れた状態で作られ**、その後は表示と非表示が切り替わるだけです。隠れている間は、
何も動きません。タイマーも、再描画ループもありません。eframe は、隠れたウィンドウを、何かが再描画を求める
まで眠らせます。それを求めるのは、プログラムのヘルパースレッドだけです。

積み場を呼び出す方法を見張る 4 つのヘルパーが、それぞれ別のスレッドで動いています。

| ヘルパー | ウィンドウを起こすとき |
| --- | --- |
| グローバルショートカット | ショートカットが押されたとき |
| トレイアイコン | クリックされたとき、またはメニュー項目が選ばれたとき |
| **ポインターの監視** | ポインターが上端に留まったとき(1 秒間に約 20 回読み取り、積み場が隠れていて設定がオンの間だけ) |
| HTTP サーバー(ワーカー 4 つ) | リクエストが届いたとき:`show`・`toggle`、またはブラウザからのメモ |

これらはウィンドウに直接触れません。チャンネルを通じて `Command`(*表示*・*非表示*・*切り替え*・
*このモニターに表示*・*終了*・ステータス行へのメッセージなど)を送り、そのあと再描画を求めます。誰も起きて
読まないコマンドは、キューの中で眠ったままになってしまうからです。ウィンドウは、毎回のパスの最初に
コマンドを読みます。隠れたウィンドウのパスでは、プログラム自身のロジック(`App::logic`)は動きますが、
描画はされないので、コマンドを処理するコストはほとんどゼロです。

表示は小さな状態機械です。*隠れている → 現れつつある → 表示中 → 隠れつつある → 隠れている*。現れるときは、
対象のモニターの上端のすぐ上にウィンドウを置いて、170 ms かけてスライドして降ろします。隠れるときは
スライドして戻したあとで隠します。ウィンドウの位置をプログラムが決められない Wayland では、ただ表示と
非表示を切り替えます。

知っておくとよい癖が 2 つあります。eframe は、何を頼んでも最初のフレームを描いたあとでウィンドウを表示
してしまうので、tsumiba はウィンドウを画面のはるか外側で起動し、トレイで待つ場合は最初のパスで再び
隠します。また、隠れたウィンドウの再描画の要求は、eframe によって 100 ms に 1 回以下に間引かれます。
`tsumiba show` からウィンドウが動くまでに 10 分の 1 秒ほどかかるのは、そのためです。

### 上端 {#the-top-edge}

ポインターの監視は、ポインターの読み取り値を受け取る小さな純粋な状態機械です。そのおかげで、画面無しで
タイミングの規則をテストできます。*最上段に触れていて、中央ゾーンにいて、十分な時間留まった(またはボタンが
押されている)、そして、ポインターが最後に離れてからまだ発火していない*。ポインターは各システム自身の
呼び出し(`GetCursorPos`、CoreGraphics、`XQueryPointer`)で読み取られ、どれも権限を必要としません。

### ループを閉じる {#closing-the-loop}

隠れるときは、ウィンドウは自分で隠れます。ポインターが(一度その上に乗ったあと)0.7 秒外れていたら、
フォーカスを失ったら、など([積み場を呼び出す](summoning.md#hiding))。メモの保存も、同じフレームごとの
ロジックが行います。編集されたメモは、最後のキー入力の 0.5 秒後に書き込まれます。

## 1 つのプロセス、たくさんの入口 {#one-process-many-doors}

すでに起動しているときに `tsumiba` を起動しても、もう 1 つは立ち上がりません。起動中のものを探し(`server.json`
に記録されたポート、次に設定のポート、そして tsumiba と答えなければならない `GET /v1/ping`)、そちらに
表示を頼みます。コマンドラインも同じ仕組みです。起動中のアプリがあれば、コマンドはその API を通り、
無ければフォルダーを直接扱います。

## ストア {#the-store}

メモはファイル `notes/<id>.md`、保存したファイルは `files/<id>/<name>`、フォルダーから導けないもの(ピン留め、
取得元、リンク)は小さな `index.json` に入ります。ID は 16 進数 20 桁で、作成時刻にランダムなビットが続くので、
古い順に並び、自分自身の作成日時を持っています。導けるものはすべて導き、フォルダーは起動時と積み場を
開くたびに再スキャンされます。これが、同期しても安全で、壊れたインデックスを再構築できる理由です
([データと同期](data-and-sync.md))。

大きなファイルのコピーでパネルが固まってはいけないので、処理は 2 段階です。*ステージ*(ストアのロックを
取らずに、バイト列をフォルダーへコピーする)と、*コミット*(一瞬だけロックを取って、エントリを
インデックスに加える)です。書き込みはアトミックです。新しいファイルを書いて、古いファイルの上に
リネームします。

## 描画 {#drawing}

ウィンドウは egui で描画されます。既定では OpenGL を使います。小さく、起動が速く、グラフィックドライバーの
あるどのデスクトップでも使えるからです。例外は、OpenGL が組み込みの 1.1 のスタブしか無い Windows
マシン(ドライバーの無い仮想マシンやリモートデスクトップのセッション)で、そこではウィンドウをそもそも
作れません。そのため Windows 版には **wgpu** レンダラー(DirectX 12。最後の手段としてソフトウェア
ラスタライザー)も含まれていて、OpenGL が失敗したときにそれを使います。ウィンドウツールキットは同じ
プロセスの中で 2 つ目のイベントループを開始できないため、この再試行は `TSUMIBA_RENDERER=wgpu` を付けて
新しく起動したプロセスで行われ、最初のプロセスはそれを待ちます。そのため、tsumiba を起動した側からは
今までどおり 1 つのプロセスに見えます。`config.toml` の `general.renderer` や `TSUMIBA_RENDERER` で、
レンダラーを明示的に選べます。このフォールバックを動かしているのは CI の GPU の無い Windows ランナーだけで、
実際の仮想マシンでは試していません。

## 文字 {#text}

egui 自身のフォントには日本語がありません。起動時にバックグラウンドのスレッドが、システムのフォントから
既知の CJK ファミリーを探し、本当に日本語の文字を持っているかを確認して、フォールバックとして加えます。
インターフェースの文字列はすべて英語と日本語の両方があり、コンパイル時の構造体によって、訳の抜けは
空白のラベルではなくビルドエラーになります。

## 資源の使用量 {#resource-use}

作者のテストマシンで、ソフトウェア OpenGL レンダラーを使った仮想ディスプレイ上では、アイドル時(隠れていても
表示されていても)、プロセスの CPU 使用は 20 秒あたり約 1〜3 ティック(10〜30 ms)で、常駐メモリは
約 176 MB でした。メモリの多くは、システムの CJK フォントとソフトウェアレンダラーによるものです。これは
ベンチマークではなく、ひとつのデータ点として扱ってください。実際の GPU があれば、メモリの様子は変わります。
